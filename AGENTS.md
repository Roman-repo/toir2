# AGENTS.md — инструкция для ИИ-ассистента по проекту ТОИР

> Прочитать перед любой работой с кодом. Краткая выжимка того, что отличает
> этот проект от произвольного репозитория 1С.

## Что это

Конфигурация **1С:Предприятие 8 — ТОИР** (техническое обслуживание и ремонт).
Платформа EDT, базируется на БСП. ~11 500 файлов, 699 МБ, 2 822 BSL-модуля.

Исходники: `Project/Toir/src/`

## Главное правило: два слоя кода

| Слой | Префикс | Действия |
|---|---|---|
| **Прикладной** | `торо_`, `гкс_` | Здесь ведётся разработка. Это «наш» код. |
| **БСП / библиотечный** | без префикса (`ОбщегоНазначения`, `Пользователи`, `РаботаСФайлами`…) | **Не править.** Перезатрётся при обновлении БСП. ~80% общих модулей (464 из 578) — чужие. |

Перед правкой модуля **всегда** проверяй префикс. Нет `торо_`/`гкс_` → скорее всего БСП.

### Как платформа определяет «можно ли править» (под капотом правила про префикс)

Эвристика по префиксу — это упрощение. Платформа определяет редактируемость через
**состояние поддержки** (`Ext/ParentConfigurations.bin`). Алгоритм:

```
1. Файла поддержки нет → поддержки нет          → редактирование РАЗРЕШЕНО
2. G = 1 (глобальный запрет)                     → read-only ВСЁ
3. G = 0 → проверяем f1 по uuid объекта:
     f1 = 0 (на замке) хотя бы у одного поставщика → ЗАПРЕЩЕНО
     f1 = 1/2 (редактируется/снято)              → РАЗРЕШЕНО
     uuid не найден                               → не на поддержке → РАЗРЕШЕНО
```

То есть наш код (`торо_`/`гкс_`) — это объекты с `f1 = 1/2` или вовсе не на поддержке;
БСП — объекты с `f1 = 0` (на замке у поставщика 1С). Преэкос достаточно для быстрой проверки,
но если сомневаешься — объект не на поддержке можно редактировать смело.

📖 [Полный алгоритм и формат ParentConfigurations.bin](https://github.com/Nikolay-Shirokov/cc-1c-skills/blob/main/docs/1c-support-state-spec.md)

## Порядок работы над задачей

**Перед началом работы** — открой [`docs/standards-cards/dispatch-map.md`](./docs/standards-cards/dispatch-map.md): это индекс-маршрутизатор «сигнал → карточки правил». Используется на этапах 1 и 4.

### Этап 1. Планирование (до написания кода)

1. **Не читай всё подряд.** Следуй [`06_Алгоритм_погружения.md`](./docs/architecture/06_Алгоритм_погружения.md).
2. **Локализуй** объекты по имени и префиксу через `find`/`grep`.
3. **Пойми связи** через карту движений ([`03_Документы_и_движения.md`](./docs/architecture/03_Документы_и_движения.md)) и поиск ссылок `grep -rn`.
4. **Прогони архитектурный чек-лист** [`docs/standards-cards/arch-checklist.md`](./docs/standards-cards/arch-checklist.md) — ответь на 7 вопросов эксперта: где жить логике, есть ли готовое в БСП/проекте, кто зависит, что через сеть, что при отказе, производительность, читаемость. Для каждого «не уверен» — остановись и переосмысли.
5. **Пройди гейт-чек-лист в [`dispatch-map.md`](./docs/standards-cards/dispatch-map.md)** — это обязательный фильтр «сигнал → карточки» **перед** таблицей A. Отметь каждое подходящее условие и открой указанные карточки. Затем уточни пакет по таблице A:
   - форма → карточки форм + (если правка XML) metadata-xml
   - запрос → карточки запросов + (если СКД) dcs-design
   - общий модуль → карточки модулей + module-templates
   - проведение → карточки событий + locks-transactions + registers-design
   - и т.д. по таблице.
6. **Прочитай отобранные карточки** — открой `.md` файлы и прочитай актуальный текст; не полагайся на память.

### Этап 2. Реализация

7. **Пиши код** по прочитанным правилам. Сверяйся с мини-чек-листом в конце каждой карточки.
8. **Перед написанием новой функции — проверь переиспользование.** `grep` по `ОбщегоНазначения.*` (БСП) и `торо_*` (прикладные). Не дублируй существующее.
9. **Комментируй «почему», а не «что».** «Что делает» видно из кода; комментарий объясняет **зачем** так, какой нюанс обходится, какое ограничение учтено. Пример:
   ```bsl
   // Блокировка до чтения: иначе два пользователя проведут одновременно
   // и получат отрицательный остаток (торо_TOIR-1234).
   Блокировка.Заблокировать();
   ```
   При обходе стандарта — комментарий с обоснованием обязателен.
10. **🔴 Не выдумывай функции.** Любая функция/метод, которая **не является 100% стандартной** платформенной (`НайтиПоКоду`, `СтрСоединить`, `Записать` и т.п.) — должна быть либо определена в проекте, либо раскрыта через стандартные средства. **Перед использованием — `grep -rn "Функция <Имя>" Project/Toir/src --include=*.bsl`.** Если определения нет и это не платформенная — **запрещено** использовать как готовую. Типичные галлюцинации: `НайтиИлиСоздать`, `ОбщегоНазначения.СоздатьЭлемент`, `ЗагрузитьТабличныйДокумент`.
11. **🔴 Сверяйся с версией платформы.** Перед использованием метода, появившегося в новой версии (`ДокументМикс`, нативный парсер `.xlsx`, `Асинх`/`Ждать`) — проверь `compatibilityMode` в `Configuration.mdo`. Проект на 8.3.12 — методы 8.3.21+ **недоступны**.
12. **🔴 UUID при создании метаданных — только случайные.** При создании нового объекта метаданных (`.mdo`/`.form`) генерируй каждый UUID заново (`uuidgen | tr 'A-Z' 'a-z'`), а **не** плейсхолдерами-последовательностями вида `a1b2c3d4-…`, `b2c3d4e5-…`. После подстановки — проверь отсутствие дубликата: `grep -rn "<новый uuid>" Project/Toir/src` (должен вернуть 0). См. [`metadata-xml.md` §4](./docs/standards-cards/practice/metadata-xml.md).
13. **🔴 Если правишь метаданные XML вслепую (без EDT/MCP) — предупреди явно.** Структуру `.mdo`/`.form` нельзя проверить синтаксически в этой среде. Если задача включает создание/правку метаданных — **обязательно скажи пользователю** в ответе: «эта часть не проверена валидатором EDT, возможны ошибки структуры». Не прячь это ограничение.

### Этап 3. Самопроверка (после написания, до коммита)

14. **Прогони [`thin-triggers.md`](./docs/standards-cards/thin-triggers.md)** — построчный проход по коду. Список теперь включает **5 слоёв**:
    - **Механические** — синтаксис, производительность «в лоб», 1С-специфика (исходный набор)
    - **Архитектура и переиспользование** — бизнес-логика в форме, дублирование, impact
    - **Производительность «каждой строки»** — обращение через точку в цикле, кэш, индексы
    - **Отказоустойчивость и читаемость** — ошибки, конкурентность, длина процедур, магические числа
    - **🔴 Галлюцинации и соответствие API** — выдуманные функции, недоступные методы версии
    Для каждого найденного триггера — открой указанную карточку и исправь.
15. **Сверь с [`docs/code-review/ЧекЛистКодРевью.md`](./docs/code-review/ЧекЛистКодРевью.md)** — по секции типа изменённого объекта.
16. **Перед коммитом** — убедись, что новый код с префиксом `торо_`/`гкс_`, без `ё` в метаданных, экспортные процедуры — с описанием. Если правились метаданные — повтори правило 13 (предупреждение пользователю).

## Принципы эксперта (цель: сеньор+)

Каждая строка кода должна быть **быстрой** и **написанной по стандартам**. Эти принципы — поверх стандартов и чек-листов; это мышление, а не механика.

| Принцип | Что значит | Как проверять |
|---|---|---|
| **Логика в правильном слое** | Форма — UI, сервер — данные/бизнес-логика | [arch-checklist §1](./docs/standards-cards/arch-checklist.md) |
| **Не дублируй** | Сначала `grep` по БСП и `торо_`, потом пиши | [arch-checklist §2](./docs/standards-cards/arch-checklist.md) |
| **Думай об отказе** | Что если сервис упал, пользователь прервал, двое одновременно? | [arch-checklist §5](./docs/standards-cards/arch-checklist.md) |
| **Каждое `ГДЕ` в индекс** | Производительность — сразу, не «потом» | [arch-checklist §6](./docs/standards-cards/arch-checklist.md) |
| **Комментарий = «почему»** | «Что» видно из кода; комментарий объясняет намерение | Этап 2, правило 9 |
| **Код для читателя** | Пишется 1 раз, читается 100; < 50 строк, осмысленные имена | [arch-checklist §7](./docs/standards-cards/arch-checklist.md) |
| **Обход стандарта — обоснован** | Если отступил от правила — комментарий с причиной | Этап 2, правило 9 |

## Соглашения об именовании (критично)

- Новые объекты — **только с префиксом** `торо_` (прикладное ядро) или `гкс_` (доработки/интеграция).
- **Буква `ё` в именах метаданных ЗАПРЕЩЕНА** (только в пользовательских текстах).
- Переменные — `ВерблюжийРегистр` с заглавной: `НомерДокумента`, `ТекущийПользователь`.
- Булевы — с вопроса: `ЭтоНовый`, `МожноРедактировать`.
- Венгерская нотация и префиксы `п`, `тз`, `вт`, `стр` — **ЗАПРЕЩЕНЫ**.
- Функции начинаются с глагола: `Получить…`, `Установить…`, `Проверить…`.
- Временные таблицы в запросах — с префикса `Вр`.

Подробности — в `CLAUDE.md` (разделы 1–2) и `standarts/std/`.
