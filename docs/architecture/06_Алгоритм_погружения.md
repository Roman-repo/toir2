# Алгоритм погружения в задачу

> Пошаговая методика. Выполняется **перед** написанием любого кода в проекте ТОИР.
> Цель: за 5–15 минут понять связи затрагиваемых модулей, не читая тысячи файлов.

---

## Шаг 1. Декомпозиция — что вообще затронуто?

Прочитайте постановку задачи и определите **тип работы**:

| Формулировка задачи | Тип | С чего начать |
|---|---|---|
| «добавить поле / реквизит» | метаданные + формы | [04](./04_Объекты_по_подсистемам.md) → найти объект |
| «изменить поведение при проведении» | документ + движения | [03](./03_Документы_и_движения.md) → какие регистры |
| «починить/изменить отчёт» | отчёт + СКД | [05](./05_Общие_модули.md) → модули-источники данных |
| «новый печатный документ» | печатная форма | поиск `Печать.` + БСП-механизм печати |
| «права / роли» | RLS, роли | [04](./04_Объекты_по_подсистемам.md) → роли подсистемы |
| «обмен / интеграция» | план обмена, XDTO | подсистемы `торо_ОбменДанными`, `гкс_Интеграция` |

**Результат шага:** список из 1–3 объектов метаданных, которых касается задача.

## Шаг 2. Локализация — где живут эти объекты?

По имени объекта (например `торо_АктОВыполненииЭтапаРабот`) определите:

1. **Тип и путь** — через [04](./04_Объекты_по_подсистемам.md) или прямой поиск:
   ```bash
   # найти папку объекта
   find Project/Toir/src -type d -name "торо_АктОВыполненииЭтапаРабот"
   ```
2. **Какие модули есть у объекта:**
   - `ObjectModule.bsl` — модуль объекта (обработка проведения, при записи)
   - `ManagerModule.bsl` — модуль менеджера (общие процедуры, печати)
   - `Forms/<ИмяФормы>/Module.bsl` — модули форм
3. **В каких подсистемах** участвует — подскажет, какие роли и интерфейсные команды задеты.

## Шаг 3. Карта зависимостей — с кем связан объект?

Это ключевой шаг для понимания «как увязаны модули».

### Если объект — документ
1. Открываем [03_Документы_и_движения.md](./03_Документы_и_движения.md).
2. В первой таблице смотрим, **в какие регистры пишет документ** → это его «выходы».
3. Во второй таблице для каждого из этих регистров смотрим, **какие ещё документы в него пишут** → это «соседи», с которыми надо согласовать изменения.
4. Читаем `ObjectModule.bsl` → процедуру `ОбработкаПроведения` (по `Движения.<Регистр>`).

### Поиск всех потребителей модуля/объекта
```bash
# кто ссылается на объект по имени
grep -rn "торо_АктОВыполненииЭтапаРабот" Project/Toir/src --include=*.bsl

# кто вызывает процедуру из общего модуля
grep -rn "торо_Ремонты\." Project/Toir/src --include=*.bsl

# где используется конкретный реквизит
grep -rn "ИмяРеквизита" Project/Toir/src/Catalogs/торо_ОбъектыРемонта --include=*.bsl
```

### Подписки на события
```bash
ls Project/Toir/src/EventSubscriptions | grep торо_
```
Показывает, на какие события (запись, проведение, удаление) завязана неявная логика — её легко упустить.

## Шаг 4. Стандарты — какие правила применять?

Открыть `CLAUDE.md` в корне проекта → раздел «Соответствие типов задач разделам индекса».
Далее читать **только релевантные** стандарты из `standarts/std/`:

| Тип задачи | Стандарты |
|---|---|
| Запросы, СКД | `queries.md`, `performance.md` |
| Модули, процедуры | `language.md`, `metadata.md` |
| Формы | `forms.md`, `ui.md`, `ux.md` |
| Роли, права | `security.md` |
| Регламентные задания | `scheduled.md` |
| Обмен данными | `integration.md` |
| Печатные формы | `reports.md` |

**Не читать все 15 файлов подряд** — только 2–5 релевантных.

## Шаг 5. Разведывательное чтение (точечное)

Принцип: **читать по 50–100 строк вокруг каждой находки, а не весь файл целиком.**

```bash
# показать процедуру с контекстом, не весь файл
grep -n "Процедура ОбработкаПроведения" -A 80 ObjectModule.bsl
```

Для крупных модулей (≥1000 строк) сначала строим оглавление:
```bash
grep -n "^Процедура\|^Функция\|^#Область" Module.bsl
```

## Шаг 6. Контрольный список перед написанием кода

- [ ] Понято, **какие регистры** затронуты (если документ) — из [03](./03_Документы_и_движения.md).
- [ ] Найдены **все потребители** изменяемого общего модуля.
- [ ] Проверены **подписки на события** для затронутых объектов.
- [ ] Прочитаны **2–5 релевантных стандартов**.
- [ ] Новое имя объекта — с префиксом `торо_` (или `гкс_`), без буквы `ё`.
- [ ] БСП-код **не правится** (если только не расширение).
