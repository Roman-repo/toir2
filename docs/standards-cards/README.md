# Карточки стандартов разработки 1С

> Практический справочник стандартов [v8std](https://github.com/zeegin/v8std) — **скилл для ИИ-модели** при разработке на 1С.
> Применим к любой конфигурации 1С:Предприятие 8, не только к ТОИР.

## Зачем этот каталог

В `standarts/std/` лежат оглавления всех ~323 стандартов со ссылками на GitHub. Здесь — **карточки**: суть правил, мини-примеры «неправильно/правильно», критичность и идентификаторы авто-проверок, без ухода на GitHub.

## Структура карточек

Каждая карточка (файл по разделу) содержит **два слоя**:

1. **Детальные расшифровки** — ключевые правила с примерами ❌/✅, критичностью, id авто-проверки. Это «горячее ядро» — правила, нарушаемые чаще всего.
2. **Таблицы заголовков** — остальные стандарты раздела (номер, название, краткая суть в 1 строку). ИИ-модель использует их как контекст: видит, что такой стандарт есть, и при необходимости открывает первоисточник.

Полный текст любого стандарта — по ссылке на [GitHub](https://github.com/zeegin/v8std), открывать в спорных случаях.

## Как пользоваться

### При разработке (ИИ-модель)
1. Определите тип задачи по таблице ниже.
2. Откройте релевантную карточку.
3. Прочитайте детальные расшифровки и таблицу заголовков.
4. Пишите код, сверяясь с мини-чек-листом в конце карточки.

### При код-ревью
1. Откройте [чек-лист код-ревью](../code-review/ЧекЛистКодРевью.md).
2. По типу объекта (документ / форма / модуль / запрос) пройдитесь по проверкам.
3. Каждая проверка связана со стандартом — кликабельно.

## Служебные карточки (поверх стандартов)

Помимо карточек по разделам стандарта, в каталоге есть 5 документов верхнего уровня — они не описывают отдельные стандарты, а связывают каталог с инструментами и архитектурным контекстом.

| Документ | Назначение | Когда использовать |
|---|---|---|
| [**retrieval-rules.md**](./retrieval-rules.md) | Словарь синонимов: фрагмент кода/тема → стандарты. Адаптация `retrieval-rules.yml` | Увидели в коде метод/фразу → сразу понять, какой стандарт открыть |
| [**diagnostics-map.md**](./diagnostics-map.md) | Карта «стандарт → диагностики» для 120 стандартов, имеющих авто-проверки (BSL LS, АПК, v8-code-style) | При ревью: нарушение должно ловиться автоматикой. При настройке CI: какие диагностики включить |
| [**patterns.md**](./patterns.md) | Паттерны проектирования (SOLID/GOF/GRASP/инженерные) с приземлением на 1С | При проектировании архитектуры: где разместить логику, как не связать систему |
| [**mcp-integration.md**](./mcp-integration.md) | Подключение к живой базе v8std через MCP (публичный/локальный) | Когда нужны самый свежий текст стандарта или объяснение конкретной диагностики |
| [**practice/**](./practice/README.md) | Практические правила кодирования и метаданных — **8 карточек**, которых нет в v8std: грабли XML, расширения, асинх/await, СКД, регистры, блокировки, скелеты модулей, типовые формы | Когда пишете код: «как именно» и «где споткнётесь» |

> Эти документы — **навигационный и практический слои** поверх карточек. ИИ-модель использует их для перехода от кода/симптомов к стандартам и обратно, а также для практических паттернов кодирования.

## Структура карточки

Каждая карточка содержит два типа записей.

**1. Детальная расшифровка** (для «горячих» правил):

```
### №Номер — Краткое название
**Критичность:** 🔴 Блокирующее | 🟡 Важно | 🟢 Рекомендация
**Суть:** 1–2 строки — в чём правило.
❌ Неправильно:     [пример кода]
✅ Правильно:       [пример кода]
🔍 Авто-проверка:   #bslls:ИмяДиагностики (BSL Language Server)
📖 Полный текст:    [ссылка на GitHub](...)
См. также:          связанные стандарты
```

**2. Таблица заголовков** (для остальных стандартов раздела):

```
| № | Название | Суть (1 строка) |
|---|---|---|
| [номер](ссылка) | Название | Краткая суть |
```

ИИ-модель при работе читает оба слоя: детальные расшифровки усваивает как жёсткие правила, заголовки — как контекст «какие ещё стандарты в разделе есть».

## Соглашения об уровнях критичности

| Уровень | Что значит | Действие при ревью |
|---|---|---|
| 🔴 **Блокирующее** | Нарушение ведёт к ошибке/блокировке/потере данных | Запрос на исправление обязателен, MR не вливается |
| 🟡 **Важно** | Влияет на производительность/читаемость/поддерживаемость | Запрос на исправление, исключения — с обоснованием |
| 🟢 **Рекомендация** | Лучше сделать так, но допустимы варианты | Замечание-предложение |
