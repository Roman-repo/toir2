# Архитектурное предложение

## Предрасчётный регистр состояния ремонта для рабочего места технического специалиста

| Параметр | Значение |
|---|---|
| **Связанный документ** | [РабочееМестоТехническогоСпециалиста-Зависание.md](./РабочееМестоТехническогоСпециалиста-Зависание.md) |
| **Решаемая проблема** | Невозможность сузить запрос списка «Ремонты» по дате: регистры периодические (положение регистратора), бизнес требует анализа интервала, а не среза на дату |
| **Тип решения** | Введение предрасчётного регистра состояния ремонта (CQRS/materialised view) |
| **Уровень проработки** | Концепция для принятия решения |
| **Дата** | 2026-07-07 |

## 1. Почему локальные правки запроса недостаточны

В отчёте о проблеме вариант № 1 («подставить параметр даты во все `СрезПоследних`») предложен как самый выгодный. Но он **некорректен для данной бизнес-логики**, и вот почему:

**Все «тяжёлые» регистры в запросе — периодические с периодичностью «Положение регистратора»** (`informationRegisterPeriodicity = RecorderPosition`):

| Регистр | Что хранит | Почему важен интервал |
|---|---|---|
| `торо_ЗаявкиПоРемонтам` | Факт ввода заявки по ремонту | Нужна вся история: заявка могла быть отменена и введена заново |
| `торо_НарядыПоРемонтам` | Факт выдачи наряда | Наряд может быть аннулирован, затем перевыдан |
| `торо_АктыПоРемонтам` | Факт выполнения акта | Акты могут корректироваться |
| `торо_ОтмененныеЗаявки` | Отмена заявки | Состояние «отменена» — это факт за весь период |
| `торо_ЗавершенныеРемонтныеРаботы` | Завершение ремонта | Завершение необратимо, проверяется за всю историю |
| `торо_ТекущееСостояниеОР` | Текущее состояние объекта | Динамика состояний во времени |
| `торо_ОстановочныеРемонты` | Связь с остановочным ремонтом | Вся история связей |

Статус ремонта (Зарегистрирован → Запланировано → Выполняется → Выполнен / Устранён) — это **производное от всей совокупности записей этих регистров**, а не snapshot на дату. Сузить запрос по дате — значит получить неверный статус. Значит, оптимизация обязана идти через **предрасчёт этого производного состояния**.

## 2. Почему именно предрасчётный регистр

Текущий запрос делает одну и ту же тяжёлую работу (разворот 10 виртуальных таблиц + анти-соединения) **на каждое обновление списка**, для каждого из множества пользователей. При этом:

- **Исходные данные меняются редко** — только при проведении/отмене 5 конкретных документов.
- **Результат расчёта почти стабилен** между изменениями.
- **Чтение происходит очень часто** — при каждом обновлении списка, у каждого пользователя, плюс фоновое автообновление каждые 3 минуты.

Это классический профиль для CQRS: переложить расчёт с пути «чтение» на путь «запись», где триггеров на порядки меньше, чем читателей.

## 3. В проекте уже есть этот паттерн — предложение его переиспользует

Архитектурно новое решение **не чужеродно** — в конфигурации уже есть аналогичный предрасчёт, проверенный временем:

| Существующий артефакт | Что делает |
|---|---|
| Регистр `торо_АктуальныеПлановыеДатыРемонтов` | Предрассчитывает плановые даты ремонта (ДатаНачала, ДатаОкончания, КрайняяДатаЗавершения). Обновляется при проведении документов. |
| Подписка `торо_ОбновитьПлановыеДатыПриПроведении` | Триггер обновления при проведении |
| Подписка `торо_ОбновитьПлановыеДатыПриОтменеПроведения` | Триггер обновления при отмене проведения |
| Общий модуль `торо_ПланированиеРемонтов` | Содержит логику пересчёта |
| Регистры `торо_СтатусыДокументов…Установленные` | Предрассчитанные статусы документов (уже работают через `СрезПоследних`) |

Предлагается **расширить ту же идею на производные поля статуса ремонта**, которые сейчас считаются «на лету».

## 4. Концепция решения

### 4.1. Новый регистр `торо_СостояниеРемонта` (рабочее название)

Непериодический регистр сведений (или периодический с положением регистратора — на выбор, см. §6), содержащий **одну строку на ID ремонта** с предрассчитанными флагами.

Эскиз структуры (концептуально, финальные имена — на этапе спецификации):

| Тип поля | Поле | Источник (что сейчас считается в запросе на лету) |
|---|---|---|
| Измерение | `IDРемонта` | `торо_Ремонты.ID` |
| Измерение | `ТипИсточника` | Внешнее основание / ППР / Выявленный дефект |
| Ресурс | `ВведенаЗаявка` (Булево) | `НЕ торо_Заявка.IDРемонта ЕСТЬ NULL` |
| Ресурс | `ЕстьНаряд` (Булево) | `НЕ торо_НарядыПоРемонтам.IDРемонта ЕСТЬ NULL` |
| Ресурс | `ЕстьАкт` (Булево) | `НЕ торо_АктыПоРемонтам.IDРемонта ЕСТЬ NULL` |
| Ресурс | `Завершен` (Булево) | `НЕ ЗакрытыеЗаявки.ID ЕСТЬ NULL` |
| Ресурс | `Отменен` (Булево) | `торо_ОтмененныеРемонты… ЕСТЬ NULL = Ложь` |
| Ресурс | `СтатусОР` (Строка) | Производное от флагов по текущим правилам `ВЫБОР…КОГДА` |
| Ресурс | `IDОсновногоРемонта` | Связь с остановочным ремонтом |
| Ресурс | `ДатаРасчёта` | Когда последний раз пересчитан (для отладки/инкрементальности) |

### 4.2. Кто и когда обновляет

Обновление — по подпискам на события проведения тех документов, что меняют исходные данные. По данным карты движений, у каждого «тяжёлого» регистра **ровно один документ-писатель**:

| Документ-триггер | Какие поля состояния invalidate |
|---|---|
| `торо_ЗаявкаНаРемонт` | `ВведенаЗаявка`, `СтатусОР` |
| `торо_НарядНаВыполнениеРемонтныхРабот` | `ЕстьНаряд`, `СтатусОР` |
| `торо_АктОВыполненииЭтапаРабот` | `ЕстьАкт`, `Завершён`, `СтатусОР` |
| `торо_ЗакрытиеЗаявокИРемонтов` | `Отменён`, `Завершён`, `СтатусОР` |
| `торо_ОстановочныеРемонты` | `IDОсновногоРемонта` |
| `торо_ВводНачальныхДанных` | (для исторических завершённых) |

Логика пересчёта — отдельная серверная процедура в общем модуле (по аналогии с `торо_ПланированиеРемонтов.ОбновитьПлановыеДаты…`). Принимает массив ID ремонтов, делает **один** пакетный запрос и записывает результат.

### 4.3. Что останется в форме

Запрос списка «Ремонты» (теперь `Form.form` ≈ 530 → ≈ 150 строк) превращается из монстра в простое чтение:

```sql
ВЫБРАТЬ РАЗЛИЧНЫЕ
    торо_АктуальныеПлановыеДатыРемонтов.ДокументНачалаЦепочки КАК Документ,
    торо_СостояниеРемонта.ТипИсточника КАК ТипДокумента,
    торо_СостояниеРемонтаСостояниеРемонта.ОбъектРемонта,
    торо_СостояниеРемонта.СтатусОР,
    торо_СостояниеРемонта.ВведенаЗаявка,
    торо_СостояниеРемонта.Завершен,
    …
ИЗ
    РегистрСведений.торо_СостояниеРемонта КАК торо_СостояниеРемонта
        ВНУТРЕННЕЕ СОЕДИНЕНИЕ Справочник.торо_ОбъектыРемонта
        ПО …
        ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.торо_АктуальныеПлановыеДатыРемонтов
        ПО …
ГДЕ
    торо_СостояниеРемонта.IDРемонта В (… по периоду из торо_АктуальныеПлановыеДатыРемонтов …)
    И ВЫБОР КОГДА НЕ &Завершенные ТОГДА НЕ торо_СостояниеРемонта.Завершен ИНАЧЕ ИСТИНА КОНЕЦ
```

- **Нет** 10 соединений с `СрезПоследних`.
- **Нет** анти-соединений `NOT IN (подзапрос)`.
- Период фильтруется по уже существующему `торо_АктуальныеПлановыеДатыРемонтов` (предрассчитанные даты).
- Объём данных на чтение — O(число ремонтов в периоде), а не O(вся история регистров).

## 5. Оценка эффекта и затрат

| Параметр | Оценка |
|---|---|
| **Эффект на чтение** | Ускорение главного запроса в **×10–50** (одно простое соединение вместо 10 виртуальных таблиц + 3 объединения). «Зависание» при смене периода должно уйти полностью. |
| **Нагрузка на запись** | +1 предрасчёт при проведении 5 документов. Расчёт идёт по **конкретным ID ремонтов** (инкрементально), а не по всей базе — дёшево. |
| **Согласованность** | Статус обновляется синхронно с проведением документа (в той же транзакции) — рассинхрона нет. |
| **Трудозатраты** | Средние: 1 новый регистр + 5–6 подписок (или расширение существующих) + 1 общий модуль с логикой пересчёта + переработка запроса формы + миграция (первичное заполнение регистра). |
| **Риск** | Средний. Основные риски: (а) пропустить документ-триггер → статус не обновится; (б) рассинхрон при ошибках проведения; (в) необходимость миграции существующих данных. |
| **Снижение нагрузки на СУБД** | Высокое: тяжёлый запрос больше не выполняется N пользователей × каждые 3 минуты. |

## 6. Открытые вопросы (на этап спецификации)

1. **Периодичность нового регистра.** Варианты:
   - *Непериодический* (простая замена 1:1) — проще, но теряется история статусов;
   - *Периодический с положением регистратора* — сохраняет историю смены статусов (может быть полезно отчётам), но чуть сложнее обновление.
   Рекомендуется обсудить с аналитиками: нужна ли история статуса ремонта, или достаточно текущего snapshot.
2. **Объединять ли с существующим `торо_АктуальныеПлановыеДатыРемонтов`** в один регистр или держать раздельно. Аргумент за объединение: меньше сущностей, одна точка пересчёта. Аргумент против: нарушение SRP, труднее аудит.
3. **Как обрабатывать ID ремонта, по которым нет ни одной записи в новом регистре** (ремонты, заведённые до внедрения, без проведения триггер-документов). Нужен регламентный регламентный задания первичного заполнения и обратной совместимости (fallback на старый расчёт для пустых).
4. **Статусы документов** (`…Установленные`) — они уже предрассчитаны и в запросе используются через `СрезПоследних`. Оставить как есть или тоже перенести в новый регистр.
5. **Нужно ли расширять предрасчёт на другие рабочие места** (`торо_РабочееМестоДиспетчера`, `торо_ОбщийПланРабот`) — они, вероятно, имеют ту же проблему и могут переиспользовать регистр.

## 7. Альтернативы (почему не они)

| Альтернатива | Почему отвергается |
|---|---|
| **Рефакторинг запроса без предрасчёта** (вариант из отчёта №№ 2,4) | Даёт ×2–4, но тяжёлая работа на чтении остаётся. Масштабируется плохо: с ростом базы зависание вернётся. |
| **Срез на дату** (изначальный вариант №1) | **Некорректен**: нарушает бизнес-логику анализа интервала (см. §1). |
| **Асинхронный пересчёт / СКД** | Переносит проблему (пользователь ждёт фонового пересчёта), меняет UX («рабочее место» перестаёт быть списком реального времени). Дороже в реализации. |
| **Кэш в памяти формы** | Не разделяем между пользователями, рассинхрон, инвалидация сложна. Не решает первичное построение. |

## 8. Рекомендация

Принять направление **«предрасчётный регистр состояния ремонта»** как стратегическое решение. На этапе спецификации:

1. Уточнить у аналитиков бизнес-требования к истории статусов (открытый вопрос №1).
2. Проверить, какие ещё рабочие места/отчёты страдают тем же запросом (№5) — возможно, регистр окупится многократно.
3. Запланировать работу в 2 спринта: (а) регистр + триггеры + миграция; (б) переработка запроса формы и регрессионное тестирование.
