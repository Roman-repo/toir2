# Отчёт о проблеме производительности

## Обработка «Рабочее место технического специалиста» — зависание при смене периода

| Параметр | Значение |
|---|---|
| **Объект** | `DataProcessors/торо_РабочееМестоТехническогоСпециалиста` |
| **Симптом** | Интерфейс «зависает» при изменении периода (и иных отборов) |
| **Тип проблемы** | Длительный серверный вызов при переформировании динамических списков |
| **Дата анализа** | 2026-07-07 |
| **Файлы затронуты** | `Forms/Форма/Form.form`, `Forms/Форма/Module.bsl`, `Forms/ФормаНастройки/Module.bsl` |
| **Архитектурное продолжение** | [РабочееМестоТехСпец-АрхитектурноеПредложение.md](./РабочееМестоТехСпец-АрхитектурноеПредложение.md) — предрасчётный регистр (стратегическое решение) |

> ⚠️ **Уточнение после обсуждения.** Вариант № 1 ниже («подставить параметр даты в `СрезПоследних`») оказался **некорректным** для данной бизнес-логики: все «тяжёлые» регистры периодические (положение регистратора), и статус ремонта требует анализа всего интервала, а не среза на дату. Стратегическое решение описано в [архитектурном предложении](./РабочееМестоТехСпец-АрхитектурноеПредложение.md). Варианты №№ 2–7 ниже остаются актуальны как тактические улучшения.

---

## 1. Постановка проблемы

Пользователь меняет параметры периода в форме настроек и нажимает «Применить» — форма рабочего места «зависает» на ощутимое время (от нескольких секунд до зависания сеанса на больших базах). Аналогичный эффект наблюдается при изменении ряда других отборов.

## 2. Цепочка воспроизведения

Восстановлена по коду. Изменение периода запускает полную переустановку всех динамических списков формы.

```
[Пользователь: форма «Настройки отбора» → «Применить»]
   │
   ▼  ФормаНастройки/Module.bsl:225  Процедура Применить
   │      └─ Module.bsl:259  Оповестить("ПерезаполнитьТаблицы", СтруктураПараметров)
   ▼
[Основная форма: ОбработкаОповещения]   Module.bsl:120
   │      └─ Module.bsl:123  УстановитьПараметрыДинамическогоСпискаКлиент()
   ▼  (контекстный серверный вызов)
[Сервер: УстановитьПараметрыДинамическогоСписка]   Module.bsl:629
   │      ├─ переустановка параметров списка «Ремонты»
   │      ├─ переустановка параметров списка «Мероприятия»
   │      ├─ Module.bsl:765  УстановитьЗапросИПараметрыДинСпискаЗаявок()
   │      ├─ Module.bsl:769  УстановитьЗапросИПараметрыДинСпискаНарядов()
   │      ├─ Module.bsl:773  УстановитьЗапросИПараметрыДинСпискаАктов()
   │      └─ Module.bsl:777  УстановитьЗапросИПараметрыДинСпискаРегламентныхНарядов()
   ▼
[Платформа: каждый динамический список перевыполняет свой запрос]
```

**Время «зависания» ≈ сумма времени выполнения всех 5 запросов списков.** Главный вклад — список «Ремонты».

## 3. Причины (по убыванию влияния)

### 🔴 Причина 1. Тяжёлый запрос главного списка «Ремонты»

**Расположение:** `Forms/Форма/Form.form:6450–6981` (≈530 строк текста запроса).

Структура запроса:

- **3 ветки `ОБЪЕДИНИТЬ ВСЕ`** (по источникам ремонта):
  1. внешние основания (`торо_ВнешниеОснованияДляРабот`) — строки 6450–6646
  2. план-график ППР (`торо_ПлановыеРемонтныеРаботы`) — строки 6649–6800
  3. выявленные дефекты (`торо_ВыявленныеДефекты`) — строки 6804–6980
- В каждой ветке — **9–10 `ЛЕВОЕ СОЕДИНЕНИЕ` с виртуальными таблицами `.СрезПоследних`**.
- **10 из этих `СрезПоследних` вызваны без параметра даты** (`СрезПоследних(, )`):

  ```sql
  РегистрСведений.торо_НарядыПоРемонтам.СрезПоследних(, )    -- нет даты, нет отбора
  РегистрСведений.торо_ЗаявкиПоРемонтам.СрезПоследних(, )
  РегистрСведений.торо_АктыПоРемонтам.СрезПоследних(, )
  ```

  Без параметра даты СУБД разворачивает **все** записи регистра до текущего момента — дорого на больших объёмах.

- **Анти-соединение через `NOT IN (подзапрос)`, повторяется во всех 3 ветках**
  (строки `Form.form:6544–6548`, `6710–6714`, `6873–6877`):

  ```sql
  И (НЕ торо_Заявка.Регистратор В
          (ВЫБРАТЬ торо_ОтмененныеЗаявки.Заявка
           ИЗ РегистрСведений.торо_ОтмененныеЗаявки))
  ```

  Это коррелированный подзапрос; СУБД не может оптимизировать его до эффективного плана.

**Нарушенные стандарты 1С:**

| Стандарт | Суть нарушения |
|---|---|
| [655](https://github.com/zeegin/v8std/blob/main/docs/std/655.md) | Ограничения при соединениях с вложенными запросами и виртуальными таблицами |
| [732](https://github.com/zeegin/v8std/blob/main/docs/std/732.md) | Запросы в динамических списках |
| [733](https://github.com/zeegin/v8std/blob/main/docs/std/733.md) | Эффективное обращение к виртуальной таблице «Остатки» (и СрезПоследних) |

### 🔴 Причина 2. Обращения через точку к реквизитам ссылок (неявные соединения)

По всему запросу: `.Ссылка.Проведен`, `.Ссылка.ПометкаУдаления`, `.Регистратор.Организация`, `.Ссылка.Организация`.

Пример (`Form.form:6911`):
```sql
И НЕ торо_ВыявленныеДефекты.Регистратор.Организация ЕСТЬ NULL
```

Каждое обращение через точку — **неявное левое соединение** с таблицей документа. В трёх объединённых ветках это умножает накладные расходы × 3.

### 🟡 Причина 3. Обновляются все 5 списков, включая невидимые

`УстановитьПараметрыДинамическогоСписка` (`Module.bsl:629`) вызывается со всеми параметрами `= Истина`. Когда пользователь на вкладке «Ремонты», списки заявок/нарядов/актов **не видны**, но их запросы всё равно перевыполняются.

### 🟡 Причина 4. `АвтоОбновление` на всех списках с коротким периодом

`АвтоОбновление = Истина`, `ПериодАвтоОбновления = 180` сек устанавливается для **всех 7 таблиц** (`Module.bsl:726,727,760,761,889,890,927,928,964,965,1052,1053,1140,1141`). С тяжёлым запросом это означает: каждые 3 минуты каждый список сам перевыполняет запрос. На многопользовательской базе — постоянная фоновая нагрузка и риск «эффекта толпы».

### 🟢 Причина 5. Баг функции `ПолучитьМассивПодчиненныхПодразделений`

**Расположение:** `Module.bsl:807–831`.

```bsl
Пока ВыборкаДетальныеЗаписи.Следующий() Цикл
    МассивПодчиненныхПодразделений = ВыборкаДетальныеЗаписи.Ссылка;  // ← ПРИСВАИВАНИЕ
КонецЦикла;
```

Функция возвращает **не массив, а последнее значение** — оператор должен быть `.Добавить(ВыборкаДетальныеЗаписи.Ссылка)`. На производительность влияет слабо, но **отбор по подчинённым подразделениям работает некорректно**.

### 🟢 Причина 6. Лишний серверный вызов `ПолучитьИтогПлановыхДней`

`Module.bsl:783` — отдельный серверный запрос на каждый вызов обновления, хотя операция (перевод периодичности в дни) тривиально считается на клиенте.

## 4. Варианты исправления

| # | Действие | Эффект | Трудозатраты | Риск | Стандарт |
|---|---|---|---|---|---|
| **1** | Подставить параметр даты во все `СрезПоследних` | 🔴 очень высокий | низкие | низкий | 733 |
| **2** | Заменить `NOT IN (подзапрос)` на `ЛЕВОЕ СОЕДИНЕНИЕ + ЕСТЬ NULL` | 🔴 высокий | низкие | низкий | 655 |
| **3** | Обновлять только активную страницу (по вкладке) | 🟡 высокий | низкие | низкий | 489 |
| **4** | Избавиться от обращений через точку | 🟡 высокий | средние | средний | 655 |
| **5** | Увеличить `ПериодАвтоОбновления` / отключить `АвтоОбновление` у невидимых списков | 🟡 средний | тривиальные | низкий | 732 |
| **6** | Починить баг с массивом (`= ….Ссылка` → `.Добавить(…)`) | 🟢 корректность | тривиальные | низкий | — |
| **7** | Считать `ИтогоПлановыхДней` на клиенте | 🟢 незначительный | тривиальные | низкий | 487 |
| **8** | Развернуть тяжёлый список в СКД-отчёт или вычисляемый регистр | 🟢 радикальный | высокие | высокий | — |

### Конкретика по топ-3

**№ 1. Параметр даты в `СрезПоследних`**

Было:
```sql
ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.торо_НарядыПоРемонтам.СрезПоследних(, ) КАК торо_НарядыПоРемонтам
```
Стало (срез на конец интересующего периода — параметр `ПлановыйПериод` уже есть):
```sql
ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.торо_НарядыПоРемонтам.СрезПоследних(&ПлановыйПериод, ) КАК торо_НарядыПоРемонтам
```

**№ 2. Анти-соединение → `ЛЕВОЕ СОЕДИНЕНИЕ`**

Было (в `ГДЕ`):
```sql
И (НЕ торо_Заявка.Регистратор В
        (ВЫБРАТЬ торо_ОтмененныеЗаявки.Заявка ИЗ РегистрСведений.торо_ОтмененныеЗаявки))
```
Стало (в `ИЗ`):
```sql
ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.торо_ОтмененныеЗаявки КАК ОтмененныеЗаявки
    ПО торо_Заявка.Регистратор = ОтмененныеЗаявки.Заявка
…
ГДЕ
    ОтмененныеЗаявки.Заявка ЕСТЬ NULL
```
СУБД использует индекс и hash-join вместо коррелированного подзапроса.

**№ 3. Обновлять только активную страницу**

```bsl
// Module.bsl, ОбработкаОповещения → ветка "ПерезаполнитьТаблицы"
Если Элементы.Страницы.ТекущаяСтраница.Имя = "СтраницаРемонты" Тогда
    УстановитьПараметрыДинамическогоСписка(Истина, Истина, Истина, Ложь, Ложь);
Иначе
    УстановитьПараметрыДинамическогоСписка(Ложь, Ложь, Ложь, Истина, Истина);
КонецЕсли;
```

## 5. Рекомендуемая последовательность работ

1. **Замер базовой линии.** Включить «Замер производительности», сменить период, зафиксировать время. Желательно снять текст реального SQL через технологический журнал (фильтр `Sql`, `Duration` ≥ 1 c) или ЦКК.
2. **Этап А (низкий риск):** правки № 5, 6, 7 — улучшения и исправление багов без изменения запроса.
3. **Этап Б (средний риск):** правки № 1, 2, 3 — оптимизация главного запроса и логики обновления. Повторить замер, ожидаемое ускорение **×3–10**.
4. **Этап В (по необходимости):** правка № 4 — устранение обращений через точку.
5. **Регрессионное тестирование:** прогнать BDD-фичи обработки (`features/`). Обязательно проверить:
   - корректность статусов ОР (Зарегистрирован / Запланировано / Выполняется / Выполнен) для всех 3 источников;
   - отбор по завершённым ремонтам;
   - отбор по подчинённым подразделениям (после правки № 6 поведение изменится — станет корректным).

## 6. Зона риска при доработках

Главный запрос списка «Ремонты» — **центральный элемент формы**, на него ссылаются:

- `ОбработкаОповещения` (`Module.bsl:97`) — обновление по событиям создания документов и закрытия ремонтов;
- обработчики отборов шапки (`Module.bsl:140–334`) — каждый `ПриИзменении` зовёт `УстановитьПараметрыДинамическогоСпискаКлиент`;
- условное оформление (`УстановитьУсловноеОформление`, `Module.bsl:1154`) — зависит от полей запроса.

Любое изменение набора полей или алиасов запроса требует синхронной правки условного оформления и проверок в обработчиках. Перед коммитом — обязательный прогон BDD-фич и ручная проверка по чек-листу из раздела 5.
